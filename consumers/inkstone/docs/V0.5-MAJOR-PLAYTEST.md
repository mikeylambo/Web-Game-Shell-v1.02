# INKSTONE V0.5 — Major Playtest Protocol

This is the first playtest protocol for the private V0.5 flagship foundation. It is deliberately split into **automated certification** and **human evidence**. CI proves the build is internally coherent; the human session proves it feels correct on real browsers, displays and controllers.

## 1. Build under test

Use the artifact produced by the green `inkstone-integration-ci` workflow for the exact commit being tested:

`inkstone-v0.5-major-playtest-<commit sha>`

Do not substitute an uncommitted dev-server build when recording certification evidence.

## 2. Automated gates required before play

A build is eligible for the major playtest only when all of these are green:

1. private Shell verification
2. Inkstone workspace install
3. V0.4 19-file feel-source parity
4. lifecycle contract
5. persistence/recovery contract
6. navigation/app-flow contract
7. browser/platform contract
8. release-certification contract
9. production Vite build
10. static production-bundle certification
11. packaged playtest artifact

Static bundle certification rejects missing release files, source maps in the public dist, and bundle-size regressions beyond the V0.5 web budgets.

## 3. Required live certification

After the build has rendered normally for at least a few seconds, open Studio (`F1`) and run:

`inkstone.certification.run`

A live PASS requires:

- legal navigation graph
- healthy persistence recovery state
- no browser release blocker
- no active WebGL recovery/fatal state
- valid player-options schema
- all required accessibility controls still present
- zero captured runtime errors
- at least 120 live presentation-frame samples
- mean frame cadence <= 20 ms
- p95 frame cadence <= 25 ms
- sampled average >= 50 FPS

The performance gate uses real `requestAnimationFrame` cadence. Background/tab-suspension gaps are excluded because lifecycle behavior is certified separately.

At the end of a session run:

`inkstone.playtest.snapshot`

This captures parity state, platform state, performance summary, diagnostics and the latest live certification result in one evidence payload.

Record each row as PASS / FAIL / NOT TESTED. Do not infer one platform from another.

| Platform | Browser | Input | Required |

Controller-brand expansion after the primary pass: DualSense/DS4, Switch Pro, third-party XInput, Bluetooth reconnect behavior.

## 5. Session A — cold boot and accessibility

Start from a clean profile when practical.

Verify:

- first boot reaches the accessibility essentials flow rather than trapping the player
- every menu is navigable without a mouse when using a controller
- text scale visibly changes menu/HUD copy
- screen shake reaches zero
- flash reduction reaches zero
- camera motion can be reduced
- high-contrast enemy tells remain legible
- hold/toggle option changes lock-on interaction as described
- deadzone and inversion controls are reachable
- fullscreen enters and exits cleanly when supported
- unsupported fullscreen remains a harmless degraded mode

## 6. Session B — full navigation walk

Drive the complete player-facing tree with the controller:

- TITLE -> PLAY
- PLAY -> PILGRIMAGE -> back
- PLAY -> SCROLLS -> back
- PLAY -> KATA setup -> back
- PLAY -> DAILY setup -> back
- TITLE -> INKSTONE -> all tabs -> back
- TITLE -> ARCHIVE -> all tabs -> back
- TITLE -> OPTIONS -> back
- TITLE -> CREDITS -> back

Watch for double-activation, lost focus, focus jumping after dynamic content, and buttons that require mouse input.

## 7. Session C — combat continuity

Play at least one meaningful run rather than only smoke-testing menus.

Required observations:

- movement and camera feel unchanged from the V0.4 baseline
- light/heavy/launcher/jump/dash/parry behavior feels unchanged
- hit-stop timing feels unchanged at default settings
- lock-on behaves correctly
- strokes and glyph recognition remain intact
- wave transitions do not corrupt input/focus
- `WAVE_CHOICE`, if enabled for testing, returns only to combat
- death beat -> Finished Calligraphy works
- AGAIN starts correctly
- SCROLLS and TITLE leave results correctly

Any combat-feel discrepancy is a stop condition because the migration is still under V0.4 parity lock.

## 8. Session D — pause/background lifecycle

During active combat:

- pause with the configured pause input
- resume explicitly
- pause and change player options
- restart from pause
- return to scroll selection from pause where allowed
- alt-tab / blur while RUN is active
- confirm the game enters the normal pause path
- return focus and confirm it does **not** auto-resume
- confirm presentation audio is suspended only for actual PAUSE
- confirm WAVE_CHOICE does not incorrectly suspend presentation audio

## 9. Session E — controller lifecycle

With a controller connected:

- navigate menus
- begin a run
- disconnect the controller
- reconnect it
- continue the session
- inspect the Studio Platform panel for connect/disconnect telemetry

The Shell observes controller lifecycle only. Inkstone's existing Input system remains responsible for actual controls, so any loss of gameplay input after reconnect is a genuine input bug rather than a Shell remapping behavior.

## 10. Session F — persistence and recovery

Normal player test:

- change several options
- complete or abandon a run
- reload the build
- verify options/profile data persisted
- verify bindings still apply

Developer recovery drill:

- inspect `inkstone.save.status`
- use `inkstone.save.restore` only when deliberately testing recovery
- use `inkstone.recovery.test` to inspect the player-safe recovery surface

WebGL drill where browser tooling permits it:

- trigger/observe context loss
- confirm the recovery surface appears
- confirm it does not expose stack traces
- confirm restoration dismisses the surface when no fatal remains
- confirm TITLE returns through legal app navigation

## 11. Performance pass

Run a representative combat sequence with effects and multiple enemies for several minutes.

Inspect:

`perf.summary`

and then:

`inkstone.certification.run`

The certification target is not a promise that every device holds 60 FPS. It is the V0.5 flagship baseline for the primary development machines and must be investigated when it fails rather than silently waived.

Also note perceptual issues that frame averages miss:

- traversal hitching
- enemy-spawn hitching
- first-use audio hitching
- glyph-recognition spikes
- gallery/results rendering stalls
- fullscreen transition stalls

## 12. Player-experience questions

After technical checks, play without debugging for one complete run and answer:

1. Does the sword still feel like a brush rather than a generic melee weapon?
2. Are strokes readable while fighting, or only after the fact?
3. Do Cross / Enso / Triad emerge naturally from combat composition?
4. Does the screen communicate wet/set/dry ink without requiring conscious UI reading?
5. Is the pause/menu shell invisible enough that the game still feels authored rather than framework-driven?
6. Does Finished Calligraphy feel like a meaningful end to the run?
7. What did you try to do that the current combat language did not let you express?
8. What was the first moment where the game felt uniquely like Inkstone?

These answers are the bridge from V0.5 foundation work into V0.6 Style/Reality design.

## 13. Stop conditions

Stop the certification session and file the issue before continuing if any of these occur:

- V0.4 parity gate is not green
- corrupted or lost profile/bindings/options data
- controller-only navigation trap
- auto-resume after focus return
- audio continuing through an actual pause unexpectedly
- unrecoverable blank WebGL canvas without player-safe messaging
- captured runtime error during normal play
- live certification failure that cannot be explained by an intentionally unsupported/degraded capability
- obvious combat-feel regression from the protected baseline

## 14. Exit criteria for V0.5 foundation

The V0.5 foundation is considered **major-playtest certified** when:

- all automated gates are green on the exact artifact tested
- primary Windows Chrome controller + keyboard rows pass
- primary macOS Chrome keyboard row passes
- at least one real controller session completes title -> run -> pause -> death/results -> replay/menu
- save persistence survives a reload
- browser blur/background behavior passes
- live certification passes after a representative combat session
- no unresolved P0/P1 release-foundation defect remains

Only then should the protected gameplay baseline be intentionally reopened for V0.6 Style/Reality work.
